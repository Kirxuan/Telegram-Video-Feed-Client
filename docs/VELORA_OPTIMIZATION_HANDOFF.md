## 1. 接手规则

接手后必须先阅读仓库根目录的 `AGENTS.md`、`README.md`，以及 `docs/ARCHITECTURE.md`、`docs/PRODUCT_SPEC.md`、`docs/DEVELOPMENT_PLAN.md`、`docs/SECURITY.md`、`docs/ACCEPTANCE_TESTS.md` 和与当前阶段相关的阶段文档。先执行只读检查，确认仓库根目录、当前分支、工作树状态和用户已有修改；不得覆盖、删除、格式化或回滚无关文件。

一次只完成一个阶段。每个阶段开始前必须写明 Outcome、Scope、Boundary、Failure states、Proof。Proof 失败时，先定位首个根因，不得继续扩展功能。除非用户明确批准，不得进入下一阶段，不得自动提交或推送。

本项目禁止在源码、文档、测试、日志或提交中出现真实 Telegram API 凭证、验证码、两步验证密码、完整手机号、会话数据或数据库密钥。不得增加权限、广告、遥测、公共存储、自建媒体代理或 Bot API。

## 2. 项目全貌

VELORA 是一个只面向 Android 的 Telegram 频道视频浏览器。用户在设备上填写自己的 Telegram API ID/API Hash，应用使用 Android Keystore 加密后保存于应用私有的 `noBackupFilesDir`，通过官方 TDLib 完成个人账号授权、频道发现、历史扫描、增量同步和文件下载。Room 只保存频道、视频元数据、标签、游标、扫描状态和缓存 LRU 元数据；视频字节只位于应用内部缓存目录。Media3 ExoPlayer 通过 TDLib DataSource 按 DataSpec 区间读取视频，当前设计只允许一个主要播放器发声，并用 owner/generation 保护当前项和下一项。UI 使用 Kotlin、Jetpack Compose、Material 3、Coroutines、Flow、Hilt、Room、DataStore、Media3 和官方 TDLib，筛选规则为频道 OR、频道与标签 AND、标签支持 OR/AND。正式产品不依赖自建服务器、广告和公共媒体存储，发布渠道为 GitHub Release，当前目标 ABI 为 arm64-v8a，最低 Android 26。

## 3. 当前事实与证据边界

- Stage 24 正式版已经完成用户自行配置凭证、签名、权限、备份排除和 ABI 静态证明。
- 工作树存在 Feed 窗口水合、TDLib 文件事件合并、缓存单写入器、R8、Baseline Profile、Macrobenchmark 和 TDLib 数据库加密等候选文件或设计，但它们不能自动视为正式能力。
- 播放性能历史证据：真实随机 Feed 曾出现约 7.5 秒首帧 P90，自然冷缺页超过 12 秒，快速反向滑动存在无首帧情况。该历史数据不是当前 Stage 25 P95 结论。
- Owner Promotion 已有负向 A/B：关闭候选时首帧 12/12、`bind→首帧` P90 约 1599ms；开启时首帧 11/12、P90 约 3033ms，P90 恶化约 89.7%。因此保持关闭，不得直接重新启用。
- 播放 ViewModel 约 1955 行，播放 Screen 约 2879 行，队列、筛选、目标交接、播放计划、错误恢复和 UI 交互高度集中。
- 本次方案整理没有重新获得 Gradle 测试、lint 或构建结果：第一次运行缺少可用 Java；设置本机 JDK 后，Gradle Wrapper 下载因网络权限失败。因此这些 Proof 当前均应标记为“尚未验证”。

## 4. 现状问题清单

### 4.1 技术架构

1. **高**：播放会话、随机轮次、页面目标、筛选、删除重排、播放计划和错误恢复集中在超大 ViewModel/Screen 中，状态竞态难以证明。
2. **高**：Feed 仍可能维护全量键快照、全量随机集合和全量标签聚合，数据规模增长后内存和查询长尾明显。
3. **高**：数据库异常在部分兼容路径中可能被包装为空列表，导致故障被显示成“没有内容”。
4. **中**：频道、视频、标签、设置和播放功能集中在 `app`，`core:common`、`core:ui` 和 feature 模块边界尚未形成。
5. **中**：当前单账号模型没有 `accountId`，未来多账号需要重新设计索引、缓存和退出清理。

### 4.2 性能与体验

1. **高**：冷缺页、随机 Feed 和快速反向滑动造成首帧长尾。
2. **高**：单播放器加 256KiB 下一项预加载受首区间、Extractor、Decoder 和 Media3 准备时间共同限制。
3. **高**：TDLib 高频 `UpdateFile`、消息更新和缓存元数据写入存在事件洪峰风险。
4. **中**：缓存 LRU 和缺失文件核对可能读取过多候选并逐条调用 TDLib。
5. **中**：约 250ms 的进度更新和大范围状态重建仍有 CPU、电量与重组优化空间。
6. **中**：Release 关闭 R8/资源压缩，启动和包体尚未完成真实基线。

### 4.3 UI/UX

1. **高**：空结果、加载失败、授权失效和数据库故障的展示语义不够明确。
2. **中**：频道页退出入口过于突出，频道/标签统计信息密度偏高。
3. **中**：320dp、200% 字体、横屏、大屏、折叠屏和无障碍动态状态尚未完成系统验收。
4. **中**：颜色、文案、间距、倒计时、按压反馈和错误映射存在重复与硬编码。

### 4.4 工程化

1. **高**：核心播放文件过大，影响测试、回归定位和多人协作。
2. **高**：工作树中的 CI、Macrobenchmark、Baseline Profile、R8 和事件合并尚未形成正式发布证明闭环。
3. **中**：README 推荐 JDK 21，而工作树 CI 使用 JDK 17，构建环境契约不一致。
4. **中**：KAPT、Compose、Room、TDLib Native 同时参与构建，增量和干净构建耗时没有统一基线。
5. **低**：历史文档中的测试通过数量不能代替当前工作树重新验证。

### 4.5 安全与稳定性

1. **高**：错误被转成空结果会造成数据正确性和恢复风险。
2. **中**：TDLib 数据库加密候选存在，但旧库迁移、密钥损坏和密钥不匹配的真机证明未完成；当前默认仍使用空数据库密钥。
3. **中**：软删除视频、标签关联和孤儿标签的清理存在延迟，长期运行会造成索引膨胀。
4. **中**：缓存所有权令牌和清理逻辑在未来并行播放器或更多预加载下有误删风险。

### 4.6 部署与成本

1. **高**：正式构建、测试、签名、APK 分析、备份排除和 GitHub Release 尚未形成一条完整的自动化证明链。
2. **中**：Release 关闭压缩会增加下载体积；TDLib Native 又构成包体物理下限。
3. **低**：无自建媒体代理和后端服务，当前服务器与隐私成本已经较低，应保留。

### 4.7 兼容性

1. **高**：Vivo/OriginOS 6/Android 16 的完整 Compose instrumentation 可能被系统 `fast_freezer`/`single-cleaner` 杀死，不能直接归因于应用代码。
2. **中**：当前仅覆盖 ARM64，未覆盖 x86、32 位 Android、iOS 和桌面端。
3. **中**：Compose、Media3、TDLib Native、Android 26 至最新 API 的组合兼容性需要设备矩阵验证。

## 5. 渐进式优化路线

### P0：先修复正确性和可观测性

#### P0-1 建立统一基线

记录首帧、首区间、重缓冲、滑动丢帧、PSS、查询耗时、TDLib 事件队列、缓存清理耗时和启动耗时，统一使用 P50/P95/P99。覆盖冷启动、热启动、自然滑动、反向滑动、冷缺页和受限网络。

**收益目标**：所有后续方案使用同一套证据比较，减少无效实验和回归定位时间 30% 以上。

#### P0-2 明确错误结果

将加载、成功空结果、成功内容、可恢复失败、重新授权和不可恢复失败分开。失败时保留上次可用内容，并提供针对性的重试或授权动作。

**收益目标**：数据库故障不再显示为假空状态；用户恢复路径缩短为单次重试或单次授权。

#### P0-3 优化查询和索引

对视频唯一键、窗口查询、标签筛选、缓存 LRU 和软删除清理做组合索引与查询计划验证，避免独立 `chatId IN`、`messageId IN` 产生过量候选。

**收益目标**：10 万条视频记录下，目标是候选行减少 70% 以上、查询 P95 降低 50% 以上，实际数值以基准为准。

#### P0-4 正式化 TDLib 事件合并和缓存单写入器

按 `fileId` 合并重复文件事件，区分授权/控制、播放和低优先级缓存事件；缓存元数据使用单写入器批量提交，并限制启动对账预算。

**收益目标**：写入量降低 60% 至 80%，洪峰期间控制事件 P95 小于 100ms。

#### P0-5 优化首区间和播放器准备

分别测量首区间请求、区间命中、Extractor、Decoder 和首帧渲染；保持 Owner Promotion 关闭。

**收益目标**：自然滑动首帧 P95 降低 20% 以上，冷缺页超时显著下降，不增加完整视频下载量。

### P1：降低复杂度并完善体验

1. 将播放进度、内容、控制和错误状态分离，缩小 Compose 高频重建范围，目标减少无关重组 30% 至 50%。
2. 对软删除、标签、孤儿记录和缓存缺失文件做批次、预算和优先级清理，避免单次清理阻塞播放。
3. 建立统一颜色、间距、文案、状态语义和无障碍规则，验收 320dp、200% 字体、横屏、大屏和折叠屏。
4. 固定本地与 CI 的 JDK、SDK、Gradle 和依赖版本，将测试、lint、构建、Compose Proof、权限、备份、ABI 和签名检查纳入发布门槛。

### P2：发布优化与数据保护

1. 先用 APK Analyzer 区分 TDLib Native、Compose、Media3 和业务代码体积，再逐步启用 R8、资源压缩和 Baseline Profile。
2. 完成 TDLib 数据库加密；新安装优先，旧库必须有迁移或重新登录路径；密钥不可读、损坏或不匹配时失败关闭，绝不回退空密钥。

## 6. 颠覆性优化路线

### D1：轻量键快照 + 有限窗口水合

用排序键和有限前后窗口替代完整 Feed 对象快照。当前内存复杂度近似随完整视频对象数量增长，新方案只保留键集合和窗口模型。对 10 万条数据，目标是将 Feed 对象相关内存降至现有的 10% 至 30%，首屏准备时间降低 40% 至 70%。代价是必须重新定义随机轮次、删除重排、标签变化和快速反向滑动的状态转移。必须用 0、1,000、100,000 条数据验证后再替换正式路径。

### D2：显式结果模型

用明确的加载、空结果、内容、可恢复失败、重新授权和不可恢复失败替换“列表为空即状态”的模型。空状态误判可由模型保证为零，失败恢复从重新进入页面缩短为单次动作；代价是需要统一数据层、ViewModel 和 Compose 的状态合同。

### D3：独立播放会话状态机

将播放目标、generation、窗口水合、播放计划、重排和所有权令牌从超大 ViewModel 中抽出，Compose 只消费稳定展示状态。目标是将无关 UI 重组降低 30% 至 50%，并使所有状态转移可以独立测试；代价是迁移期间需要保证旧路径与新会话不产生双重控制。

### D4：分级事件总线与预算化写入

让授权和控制事件优先、播放事件次之、缓存统计批量合并，按 `fileId` 和缓存键去重。目标是将重复写入降低 60% 至 80%，控制事件 P95 小于 100ms；主要风险是错误的合并规则可能丢失删除或内容更新，因此必须保留启动对账和最终一致性校验。

### D5：单播放器 SampleQueue

在单播放器内部提前准备下一项的媒体样本，保留现有所有权令牌和安全边界。与已知基线相比，必须至少进行 30 次样本，首帧成功率达到 100%，P95 至少改善 15%，且没有黑帧、错帧、双音频、Codec 错误或误删。未达到门槛不得默认启用。

### D6：固定容量双播放器池

仅保留 ACTIVE 和 STANDBY 两个播放器，STANDBY 不获取音频焦点。目标为首帧 P95 至少改善 15% 且绝对改善至少 75ms；PSS 增量不超过 25% 或 64MiB，Jank 增量不超过 2 个百分点，并且不得出现双音频、黑帧、错帧和 Codec resource error。该方案资源、热量和生命周期风险显著高于单播放器，只在 D5 无法达标时评估。

### D7：自动化发布证明系统

将 R8、资源压缩、Baseline Profile、APK 分析、启动基线、JNI/反射回归、签名、权限、备份、ABI 和 Compose Proof 组成单一发布门槛。目标是 APK 体积减少 8% 至 20%、冷启动改善 10% 至 25%，但不对固定包体数字做承诺，因为 TDLib Native 存在物理下限。

### D8：严格的 TDLib 数据库密钥生命周期

用 Keystore 保护 TDLib 数据库密钥，密钥不可读、损坏或不匹配时失败关闭并重新授权。目标是把同步和启动额外开销控制在 5% 至 10% 内，同时提升本地会话和频道索引的静态保护等级。旧版本升级、卸载重装、备份恢复和设备密钥异常必须全部演练。

## 7. 分阶段执行顺序

### 阶段 0：基线与环境合同

**Outcome**：得到可重复的构建、测试、首帧、查询、事件和内存基线。

**Scope**：只读检查、构建环境、指标采集、设备矩阵和发布证据目录。

**Boundary**：不改变业务逻辑，不启用 Owner Promotion、双播放器或数据库加密。

**Failure states**：构建环境不可用、设备不可达、网络受限、指标缺失必须明确记录。

**Proof**：执行仓库既定的测试、lint、debug 构建和 Compose Proof；当前尚未验证。

### 阶段 1：错误语义、缓存写入和清理

先完成 D2 的结果模型、P0-4 事件合并、软删除与缓存清理规则。通过数据库故障、授权失效、TDLib 事件洪峰、文件缺失和退出账号场景证明恢复行为。

### 阶段 2：查询和 Feed 窗口化

先完成 P0-3，再做 D1。使用 0、1,000、100,000 条数据验证查询 P95、内存、首屏、删除重排和快速反向滑动。

### 阶段 3：播放会话与首帧实验

完成 D3 后，依次验证首区间优化和 D5 SampleQueue。Owner Promotion 继续关闭。只有达到 D5 的完整门槛，才允许进入候选发布。

### 阶段 4：体验与兼容性

完成 UI 状态重建范围优化、视觉令牌、无障碍、320dp/200% 字体、大屏、横屏、折叠屏和设备矩阵验收。Vivo 的系统冻结现象应按仓库 Compose Proof 规则处理，不能重复同一条已知会被系统杀死的 instrumentation 命令。

### 阶段 5：发布和安全加固

启用并验证 R8、资源压缩和 Baseline Profile；随后完成 D8 数据库加密迁移演练。最终验证正式签名、权限、备份排除、ABI、凭证文件、TDLib 数据库、媒体缓存和 Release 包边界。
